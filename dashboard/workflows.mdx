Workflows are AI automations that keep your docs current by opening pull
requests. They live under **Agents › Workflows** at `/workflows`. Because they
open pull requests, they require docs-as-code mode with a connected GitHub repo,
and they're available on the Value plan.

<Image src="/docs/images/dashboard/workflows.png" alt="The Workflows page, showing the Value-plan upgrade prompt for docs automations" />

<Callout type="info">
  Workflows need the **Value** plan (or Enterprise) and a connected GitHub repository. In
  editor-only mode there's no repo to open pull requests against. See
  [Billing](/docs/dashboard/billing).
</Callout>

## How workflows work

A workflow runs on a trigger, inspects your docs, and (when it has a change to propose) opens a pull request. You review the pull request in GitHub and merge
it like any other, so nothing changes without your approval.

## The Workflows and Runs tabs

The Workflows page has two tabs:

- **Workflows** (`/workflows`) — lists every workflow you've configured. Each
  row shows the workflow name, trigger type, connected repositories, and the
  status of its most recent run. From here you can click **Run now** to trigger
  a workflow immediately, or **Edit** to change its configuration.
- **Runs** (`/workflows/runs`) — the full run history for all workflows. Use
  the workflow dropdown to filter to a single workflow, and the status pills to
  filter by outcome (completed, failed, running, and so on).

When you click **Run now**, the dashboard switches to the Runs tab so you can
watch the run as it happens.

## Templates

Velu ships templates for common docs upkeep:

- **Changelog generation**: draft changelog entries from merged changes.
- **API-doc sync**: update reference docs when your API changes.
- **Translations**: keep translated pages in sync with the source.
- **Style-guide enforcement**: flag and fix wording that breaks your style
  guide.
- **Typo check**: catch spelling and grammar mistakes.
- **Broken-link detection**: find links that no longer resolve.
- **SEO audit**: check pages for missing titles, descriptions, and metadata.

## Autopilot

Autopilot is a workflow template for Enterprise workspaces. It keeps your pages,
screenshots, and videos accurate as your product changes. For each change it
reviews, Autopilot revises the pages the change affects, writes pages for new
features, and re-records the screenshots and videos of the screens the change
touched. It then opens a pull request on your docs repository for you to review.

Use Autopilot when your product UI changes often and you want visuals to stay
current without recording them by hand. Autopilot has a fixed job, so there is no
prompt to write. Autopilot appears in the template list only when it is available
for your workspace.

To set it up, choose **Autopilot** on the template picker and configure:

- **Trigger**: run when a pull request is merged, or on a schedule. A scheduled
  run reviews every commit since the previous run. You can switch between the two
  triggers later by editing the workflow.
- **Trigger repository**: the code repository to watch.
- **Context repositories**: other repositories Autopilot can read. If your first
  docs build used repositories, they are added for you, apart from the trigger
  repository. You can change the list.
- **Screenshots**: update screenshots of the screens a change touches, and add
  them for new features. On by default.
- **Videos**: re-record videos of the steps a change touches, and record new ones
  for new features. On by default.

## Triggers

Each workflow runs either:

- **On pull-request merge**: after a pull request lands on your default branch.
- **On a schedule**: at a recurring time you set.

## Before your docs repository exists

If you have connected GitHub but your first build is still writing your docs, the
Workflows page shows **Your docs are still being built** with a **See progress**
button. Workflows open pull requests on your docs repository, which the first
build creates when it publishes, so you can set them up once your site is live.
If the first build did not finish, the page says so and the button reads **Go to
the build**.

## Failed runs

When a run fails, the Runs tab shows the specific reason recorded for that run
instead of a generic message. Hover over the error text to see the full detail.

## Cost

Each completed run is charged its actual cost in credits, drawn from your plan's
monthly allotment or purchased balance. A run needs at least 140 credits in your
balance to start, and a single run never costs more than 1,400 credits. The Runs
tab has a **Credits** column that shows what each completed run used. Skipped and
failed runs aren't charged and show a dash. See
[Billing](/docs/dashboard/billing) for credits and top-ups.
